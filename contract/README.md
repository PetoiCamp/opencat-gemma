# Contract

`<robot>.json` (`bittle.json`, `nybble.json`, `quaddle.json`) is the single source of truth for what Gemma may send to that robot. The Gemma prompt and the output schema are generated from them.

## Fields

```json
{
  "robot": "Bittle X robot dog",
  "model": "Bittle",
  "ble_prefix": "bittle",
  "codes": { "kwkF": {"meaning": "walk forward", "kind": "steps"}, "XO": {"meaning": "...", "kind": "final", "echo": "k"} },
  "examples": [ ["walk forward then sit", ["kwkF", "ksit"]] ]
}
```

- `robot`: used in the first line of the prompt ("You control a Petoi ...").
- `model`: the name the robot reports to `?`. USB, Bluetooth and Wi-Fi detection look for it in the reply.
- `ble_prefix`: the start of the robot's advertised Bluetooth name, lowercase. The Bluetooth scan tries these names (and `Petoi...`).
- `codes`: every allowed command (69 for Bittle X, 52 for Nybble Q, 100 for Quaddle), generated by `tools/build_contract.py` (see the main README, "Adding a robot"). Quaddle's are the union of the command table of the firmware author's Gemma prompt and the web-coding list (`--prompt-table <file> --firmware ... --web ... --exclude <codes>`); a code in both keeps the prompt table's meaning and kind. That prompt is not part of this repo. `meaning` goes into the prompt. `kind` says how the starter sends it:
  - `steps`: accepts an optional step count of 1 to 20 (`kwkF 5`). The starter always adds a count (default 3), so the walk ends by itself.
  - `timed`: sent with no number. The computer waits a few seconds, then sends `kbalance`. Used for turns, because angle turns never stop on firmware B10_260527.
  - `once`: sent as is, and the robot reports when it is done.
  - `joint` (Quaddle `m0`, `m8`, `m9`): always followed by a space and an angle from -90 to 90 (`m0 45`, `m8 -30`).
  - `final` (Quaddle `XO`, `Xo`): sent as is, and must be the last command; anything after it is dropped with a warning. `XO` is refused over Bluetooth, because it disconnects the link.
- `echo` (optional): the line the robot prints when this command is done, if it isn't the command's first letter. `XO` and `Xo` finish with `k`, so they carry `"echo": "k"`; the USB and Bluetooth links wait for that line instead.
- `examples`: `[request, [commands]]` pairs shown to Gemma in the prompt. Examples are the only thing to tune when Gemma gets a case wrong. Each robot keeps its own examples, using only its own codes (Quaddle walks backward with `kbkF`, not `kbk`).

## How the prompt and schema are built

`opencat_gemma/contract.py` builds one regex from the codes:

```
^((<steps codes>)( ([1-9]|1[0-9]|20))?|(<joint codes>) -?(90|[1-8]?[0-9])|<other codes>)$
```

The joint part is left out when a robot has no joint codes.

The schema is `{"type": "array", "items": {"type": "string", "pattern": <regex>}}`. The prompt is the examples, the code list, a sentence about step counts (and, for Quaddle, about joint angles and that `XO`/`Xo` come last), and the "return [] if nothing matches" rule.

## Changing it

Edit the JSON, then regenerate:

```bash
.venv/bin/python -m opencat_gemma.contract
```

This rewrites `<robot>.prompt.txt` and `<robot>.schema.json`. The tests fail if you forget (`test_generated_files_are_in_sync`). Then re-check Gemma with `eval/run_eval.py`.

## Using it on Android or in another language

- Load `<robot>.prompt.txt` (e.g. `bittle.prompt.txt`) as the system prompt.
- If your runtime supports constrained output, use `<robot>.schema.json` for it.
- **Always** validate every command against the same regex before sending it to the robot, even when the output was constrained. Models and runtimes differ, and the check is what keeps any code outside the contract off the robot.
