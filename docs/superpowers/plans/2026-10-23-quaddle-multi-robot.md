# Multi-robot Support (Quaddle) Implementation Plan (Plan 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Support Petoi **Quaddle**, which runs the ESP32-S3 firmware family, alongside Bittle X and Nybble Q, which run the ESP32 BiBoard family. Adding the next robot should take a data file, not code changes.

**Architecture:**
- **Robot registry.** Each robot is one `contract/<robot>.json` with its commands, plus two new fields:
  - `model`: the name the robot reports to `?`;
  - `ble_prefix`: the start of its advertised BLE name.

  Detection (`robot_from_reply`), the BLE scan, and the CLI's `--robot` choices all read the registry. Nothing is hardcoded.
- **Contract generator,** committed as `tools/build_contract.py`. It builds a robot's command list from Petoi's **public** web-coding skill table (`motion_skills.js` + `translations.js`), keeping only codes that exist in a given firmware's skill table. It works with any firmware checkout, both BiBoard and S3.
- **BLE handshake that works with both firmware families.**
  - ESP32 firmware pushes `Petoi <MODEL>` on connect and then forces a rest `d`.
  - S3 (NimBLE) firmware stays silent until it receives `?`.
  - So `BleLink.connect()` waits briefly for a pushed greeting (and its `d`), then **always** identifies the robot with `?`.
- **Per-robot eval:** `eval/cases.<robot>.json`, with fallback to `eval/cases.json`.

**Tech Stack:** Same as before. No new dependencies.

## Context

### Privacy (Kai, 2026-10-23)
- The S3 firmware is a private repo.
- **Public files (code, docs, this plan) describe behaviour only:** no S3 file names, line numbers or code.
- Exact source references go in the local, uncommitted `QUADDLE_S3_NOTES.md`.
- Quaddle's command names and labels come from Petoi's public web-coding tool, which already lists them.

### Shared behaviour (read from both firmware sources, BiBoard verified on hardware)
- **Serial:** `k…` commands, the `k` "done" echo, and `?` returning the model name.
- **Step-count walks** (`kwkF 3`) report done only when finished.
- **The same angle-turn mechanism,** so the "angle turn never stops" bug may also apply. Unverified on Quaddle.
- **The same Nordic UART BLE UUIDs.**
- **The same WebSocket server** on port 81, including rejecting a new task while one runs.
- **BLE names** are `<Model><2 hex digits>_BLE`.

### Quaddle differences (read from the S3 source, unverified on hardware)
- **Model name:** `Quaddle`. It has 6 DOF (a 2-servo head plus 4 legs), so its skill set is its own.
- **BLE names:** `Quaddle<2 hex>_BLE`, with `Petoi_BLE` as a fallback name.
- **BLE handshake:**
  - **no greeting and no forced rest on connect;**
  - on `?` it replies `Petoi Quaddle`, then `u`, then `Quaddle`, then `<version>` (e.g. `Q_260529`), then `?`.
  - The firmware mentions answering `?` "after write ACK", so writes may need `response=True`. **Task 0 checks this.**
- **Unverified:** whether step counts work for its `…F` gaits; what its `…B` (backward) gaits and `kvt90L` do; whether angle turns stop. **Task 0 checks these.**

## Decisions (proposed, for Kai to approve)

1. **Quaddle contract:** generated by `tools/build_contract.py` from the public web-coding entries tagged `quaddle`, keeping only codes present in the S3 Quaddle skill table.
   - Excluded: the setup tools `kcalib`, `kzero`, `kts`.
   - Kinds:
     - a walk ending in `F` is `steps`;
     - other walks are `timed`, **until Task 0 shows otherwise**;
     - everything else is `once`.
2. **Quaddle prompt examples** may differ from Bittle's. Quaddle has `kbkF`, not `kbk`. Each contract keeps its own examples, and each must contain only that robot's codes.
3. **`?` is the identity check over every link.** The BLE greeting is no longer used for identification, only waited for (on ESP32) so commands aren't overwritten by the forced `d`.
4. **No commits until Kai says so.** This plan and the generator get committed later, behaviour-only.

## Addition (2026-10-23): choosing your robot when several are nearby

**Problem (Kai).** In a hackathon room, `--bluetooth` connects to the **strongest** Petoi signal, which may be another team's robot. Each person needs to know their robot's Bluetooth name and choose it explicitly.

**Firmware facts (both families, from source; reply format not yet verified):**
- **`n` on its own** prints the robot's stored name.
- **`n<NAME>`** (at most 16 characters) sets a new name, effective at the next boot.
- **BLE name:** the robot advertises as `<name>_BLE`. Default names look like `Bittle0D`, `Quaddle03`; custom names can be anything, e.g. `Team7`.

### Decisions (proposed)
Note: changed from `--bluetooth NAME` to `--name` (a value-taking `--bluetooth` swallowed the request).

1. **Never silently pick between robots.** `--bluetooth` with no name:
   - connects only if **exactly one** Petoi robot is found;
   - if several are found, lists them (name and signal) and exits, asking for `--bluetooth --name NAME`.
2. **`--bluetooth --name NAME`** connects only to the robot whose advertised name equals `NAME` or `NAME_BLE` (case-insensitive), **whatever its prefix,** so custom names like `Team7_BLE` work. It's still identified with `?`.
3. **`--robot-name`** (over USB or `--port`): prints the robot's Bluetooth name, e.g. `Your robot's Bluetooth name: Quaddle03_BLE`.
   - **`--robot-name NEW`** renames it: at most 16 characters, letters, digits, `-` and `_` only.
   - Afterwards it prints: switch the robot off and on, then use `--bluetooth --name NEW`.
4. **README section "Several robots in one room":**
   - find your robot's name with `--robot-name` over USB;
   - optionally rename it to your team name;
   - always connect with `--bluetooth --name <name>`.
   - Plus the system-device-list note (disconnect it there first).
